# 2026-11-08

## 新建项目：ReSettle（本地重实现 getresettle.com）

MacBook + 2 台外接屏（内置 2056×1329@(0,0)、P2768T 3360×1890@(0,-1890)、VX2479 竖屏 1440×2560@(-1440,-1473)），
息屏后窗口布局被系统打乱。做了个 Swift 菜单栏 App 来记布局 + 唤醒后还原。

**产物**
- `Package.swift` + `Sources/ReSettle/**`，`build.sh` 组装 `dist/ReSettle.app`（Apple Development 证书签名）
- 代码结构：`Core/{Engine,DisplayManager,WindowSampler,WindowMatcher,Restorer,Geometry,LayoutDeviation,LayoutStore,TabGroupsBridge,SelfTest}` + `MenuBarController` / `SettingsUI` / `Diagnostics`

**关键设计决定（别改坏）**
1. 记忆按「显示器指纹集合」哈希成 `setupKey` 分桶。折叠后的布局天然落到另一个 key，不会污染原 profile。
2. 记录前必须冻结：`CGDisplayIsAsleep` 全灭 / 屏幕锁定 / 配置变更中 → 不记录。另有 `looksCollapsed()` 二次确认（跨多屏 → 全挤一屏且窗口没少，要求连续两次才认）。
3. 恢复必须「收敛」：每个窗口设完读回核对，最多 3 轮。只设一次时实测 13/19 成功，加收敛后 19/19。
4. 偏差判据：位置 >8pt 算乱，尺寸 >48pt 才算乱（有些 App 每次会自己改几十像素高度）。
5. WindowMatcher 四级：窗口号 → 标题 → **位置就近（全局贪心）** → 数组顺序。只按顺序会配反，实测会误判「布局不一致」。

**TabGroups 协作（重要）**
`TabGroups/` 是用户的窗口拼贴工具源码。读 `Container.swift` 得到硬事实：
`containerWindowFrameChanged → frame = newFrame; layout()`（壳一动就重排窗格）；
`handleChildEvent(.moved) → 0.15s 后把窗格拽回`。
⇒ 策略：**先还原容器壳（`tech.ripplex.tabgroups`，height ≥ 200），等 280ms 让它 layout，再还原其余窗口**。
❌ 试过并废弃：用「窗口是否被容器矩形包住」来排除窗格 —— 铺满屏的容器会误伤背后所有窗口（19 个里误排 9 个）。

**踩过的坑**
- TCC 记在「责任进程」上：从终端跑 `--dump` 时 `AXIsProcessTrusted()` 反映的是终端，不是 App。要看真实状态用 `kill -USR1 <pid>`（App 进程内写 dump.txt）。
- SwiftPM 在本环境报 `sandbox-exec: sandbox_apply: Operation not permitted`，`build.sh` 里加了 `swift build --disable-sandbox`。
- 用 Apple Development 证书签名（而非 ad-hoc），TCC 按「证书 + Bundle ID」记账，重编译不用重新授权。

**验证手段**
- `kill -USR1 <pid>` → dump.txt（显示器、profile、当前布局、`layout vs memory`）
- `kill -USR2 <pid>` → selftest.txt（所有窗口挪 48pt → 按记忆还原 → 逐窗口核对）
- 最终实测：19 windows sampled / 17 nudged / 17 applied / 17-17 verified / PASS
- `pmset displaysleepnow` + `caffeinate -u -t 3` 验证过真实息屏→唤醒链路

## 追加：时间模型重做（用户指出 5 秒息屏测不出真问题）

用户质疑得对：5 秒息屏不会让 Mac 断开显示器电源、重建桌面空间，正事没测到。
而且旧代码确实有病：唤醒后 1.6s 就可能动手，连续两次"看起来对"就在 ~4s 收工开始记录——
正好卡在 macOS 重建的中段。**真正的危险不是抢窗口，是把半成品布局记成新基线（永久污染）**。

改成「等信号安静」而不是「等固定秒数」。三个闸门同时满足才动手：
1. `now - lastDisplayEventAt >= 2s`（显示器事件：reconfig / didChangeScreenParameters / activeSpaceDidChange）
2. `now - stableSince >= restoreDelay`（默认 4s，窗口坐标没动）
3. `now - wakeAt >= restoreDelay + 1`

写盘闸门更严：唤醒后 60s、显示器事件后 8s、稳定不足 4s 一律不写。
允许动手的总窗口 35s（够 macOS 重建，又不会把用户醒来自己拖窗口也纠正回去）。
恢复后 5s 复核，还偏就补一轮（`onlyDeviating: true`，只补没到位的），最多 2 轮。

新增 `kill -WINCH` 模拟测试（不碰系统状态，只喂信号模式）：
t+0 唤醒 → t+0~6s 每 0.4s 一次"还在动" → t+2 / t+4.5 各挪一轮 50pt 且不还原。
结果：churn 期间 0 次恢复、0 次写盘；churn 停止后 +10s 才动手，18/18 回位，PASS。

顺带修掉：`wakeAt == distantPast` 时日志打出 `+63929839721.0s` 的错；
`noteDisplayActivity` 不再延长 `watchUntil`（否则每次切 Space 都重开纠正窗口）。

## 追加：菜单动作实测（用户问"菜单里功能都可用么"）

新增 `kill -ALRM` 冒烟测试：按菜单真实结构 `sendAction` 逐个触发，结果写 `menu.txt`。
实测全过：Remember(20 windows) / Restore Now(moved 0，因为本来就对) / Undo / Auto-Restore 开关(t→f→t) / Settings 窗口真的可见。
`kill -USR1` 的 dump 里现在也带整棵菜单树（每项的 action / target / callable）。

`LoginItem.statusDescription` 返回 "Not found (move app to /Applications)"。拖到 /Applications 后即可。
